# Glossary term registry (merged from drafters)

- **Relational model** — A way of storing data as tables of rows linked by key values and queried declaratively, proposed by E. F. Codd in 1970. (ch02)
- **Primary key** — The column or set of columns that uniquely identifies each row in a table. (ch02)
- **Foreign key** — A column whose values must match the primary key of another table, linking related rows. (ch02)
- **Join** — A query operation that combines rows from two or more tables on matching key values. (ch02)
- **Normalization** — Structuring relational tables so each fact is stored exactly once, avoiding update anomalies. (ch02)
- **Denormalization** — Deliberately duplicating data across records to make common reads cheaper at the cost of harder updates. (ch02)
- **Declarative query** — A query that states the result wanted and leaves the execution method to the database optimizer, as in SQL. (ch02)
- **Document database** — A database that stores self-contained JSON-like records (documents), such as MongoDB. (ch02)
- **Schema-on-read** — An approach where data structure is interpreted when data is read rather than enforced when it is written. (ch02)
- **Key-value store** — A database that stores and retrieves an opaque value by its unique key, like a distributed hash table. (ch02)
- **Partition key** — The attribute whose hashed value decides which partition or node stores a record. (ch02)
- **Wide-column store** — A database of sparse rows grouped by partition key and sorted by clustering key, descended from Google Bigtable. (ch02)
- **Property graph** — A graph data model of nodes and edges where both can carry key-value properties. (ch02)
- **RDF** — Resource Description Framework, a graph model of subject–predicate–object triples queried with SPARQL. (ch02)
- **Graph traversal** — Answering a query by following edges from node to node, with cost proportional to edges touched. (ch02)
- **GQL** — Graph Query Language, the ISO/IEC 39075:2024 standard for querying property graphs, largely based on Cypher. (ch02)
- **Time-series database** — A database tuned for time-stamped, append-mostly measurements and window aggregations. (ch02)
- **Inverted index** — A search index mapping each term to the list of documents that contain it. (ch02)
- **BM25** — The standard keyword relevance-scoring function used by Lucene, Elasticsearch and OpenSearch. (ch02)
- **Embedding** — A numeric vector produced by a model so that items with similar meaning lie close together. (ch02)
- **Approximate nearest neighbor** — Similarity search that trades a little recall for large speed gains, using indexes such as HNSW. (ch02)
- **Multi-model database** — A single database engine that supports several data models, such as tables, JSON documents and vectors. (ch02)
- **Cypher** — Neo4j's declarative property-graph query language and the main basis for ISO GQL. (ch02)
- **Valkey** — The Linux Foundation's BSD-licensed fork of Redis 7.2.4, created in March 2024. (ch02)
- **Open table format** — an openly governed metadata layer and commit protocol that turns a collection of files on object storage into a transactional table with snapshots and schema evolution. (ch07)
- **Snapshot isolation** — a guarantee that each reader sees one consistent committed version of the data, unaffected by writes in progress. (ch07)
- **Time travel** — querying a table as it existed at an earlier snapshot, version or timestamp. (ch07)
- **Table metadata file** — Iceberg's JSON root file holding a table's schemas, partition specs, properties and snapshot list; the catalog points to the current one. (ch07)
- **Manifest list** — an Iceberg file listing the manifests that make up one snapshot, with partition-range summaries used to skip manifests. (ch07)
- **Manifest** — an Iceberg Avro file listing data or delete files with their partition values and per-column statistics. (ch07)
- **Delta log** — the `_delta_log` directory of numbered JSON commit files that records every change to a Delta Lake table. (ch07)
- **Delta checkpoint** — a Parquet file summarising a Delta table's full state at one version so readers need not replay the whole log. (ch07)
- **Hudi timeline** — Apache Hudi's ordered record of table actions (commits, compactions, cleans), each moving from requested to inflight to completed. (ch07)
- **Hidden partitioning** — Iceberg's practice of deriving partition values from column transforms so queries filter on ordinary columns and never reference partitions. (ch07)
- **Partition evolution** — changing a table's partitioning scheme for new data without rewriting existing files. (ch07)
- **Schema evolution** — safely adding, dropping, renaming, reordering or widening columns over a table's life without rewriting data. (ch07)
- **Compare-and-swap** — an atomic operation that updates a value only if it still equals an expected value; the primitive behind table-format commits. (ch07)
- **Optimistic concurrency control** — a scheme where writers work without locks and validate at commit time, retrying if another writer committed first. (ch07)
- **Copy-on-write** — applying row-level changes by rewriting the affected data files in full, making writes costly and reads simple. (ch07)
- **Merge-on-read** — applying row-level changes by writing separate delete or change records that readers merge at query time until compaction. (ch07)
- **Delete file** — an Iceberg v2 file recording deleted rows either by file position or by column values. (ch07)
- **Equality delete** — a delete expressed as column values (for example id = 5), cheap for streaming writers but expensive for readers. (ch07)
- **Deletion vector** — a compact bitmap marking which row positions in one data file are deleted, used by Delta Lake and Iceberg v3. (ch07)
- **Small-files problem** — the slowdown and overhead caused when a table accumulates many undersized data files, typically from frequent streaming commits. (ch07)
- **Compaction** — a maintenance job that rewrites many small or delete-laden files into fewer, larger, often sorted files. (ch07)
- **Snapshot expiration** — removing table snapshots older than a retention window so files they alone reference can be physically deleted. (ch07)
- **Orphan file** — a file in a table's storage location that no snapshot references, typically left by a failed or abandoned write. (ch07)
- **Catalog-managed table** — a Delta Lake table (4.1+) whose commits are ratified by its catalog rather than by the filesystem. (ch07)
- **Iceberg REST catalog** — the open HTTP API specification through which engines load, commit to and increasingly plan scans on Iceberg tables. (ch07)
- **UniForm** — Delta Lake's Universal Format feature, which writes Iceberg (and Hudi) metadata alongside the Delta log so other engines can read one copy of data. (ch07)
- **Apache XTable** — an incubating Apache project that translates table metadata between Iceberg, Delta Lake and Hudi without copying data files. (ch07)
- **DuckLake** — a lakehouse format from the DuckDB team that stores all table metadata in a SQL database and data in Parquet. (ch07)
- **Data inlining** — DuckLake's technique of storing very small inserts, updates and deletes in the catalog database instead of writing new files. (ch07)
- **Puffin file** — Iceberg's file format for auxiliary blobs such as statistics sketches and v3 deletion vectors. (ch07)
- **Conditional write** — an object-store write that succeeds only if a precondition holds, such as the object not already existing. (ch07)
- **Row lineage** — Iceberg v3 tracking of a stable row ID and last-updated sequence number for each row. (ch07)
- **Lakehouse** — an architecture that provides warehouse-grade management and performance over open file and table formats on object storage. (ch07)
- **ACID** — atomicity, consistency, isolation and durability: the guarantees that make database transactions safe. (ch07)
- **LSM-tree** — a log-structured merge tree, a write-optimised structure that buffers writes and merges sorted runs in the background. (ch07)
- **Parquet** — the dominant open columnar file format for analytics, used beneath all major table formats. (ch07)
- **Object storage** — flat, HTTP-accessed storage of immutable objects addressed by key, such as Amazon S3. (ch07)
- **Metastore** — a service that stores table definitions, schemas and locations so query engines can find data; the Hive-era name for a technical catalog. (ch08)
- **Technical catalog** — the on-path service that resolves a table name to its current metadata, arbitrates atomic commits and enforces access policy for every engine. (ch08)
- **Business catalog** — a tool for people to discover, understand and trust data through search, a business glossary and stewardship workflows (e.g., Collibra, Alation, Atlan). (ch08)
- **Hive Metastore** — Apache Hive's Thrift service backed by a relational database that records tables, columns and partitions; the first widely shared lakehouse catalog. (ch08)
- **Credential vending** — a catalog issuing short-lived storage credentials, scoped to one table's prefix, to an engine it has authorized. (ch08)
- **Remote signing** — a catalog signing each object-storage request on an engine's behalf instead of handing out credentials. (ch08)
- **Catalog federation** — one catalog discovering, governing and querying tables that are registered in another catalog without copying them. (ch08)
- **Namespace** — a hierarchical container, such as a database or schema, that groups tables inside a catalog. (ch08)
- **Metadata pointer** — the catalog's record of which metadata file represents a table's current version; swapping it atomically is an Iceberg commit. (ch08)
- **OLTP** — Online transaction processing: many small, fast, correct reads and writes that record business events such as orders and payments. (ch01)
- **OLAP** — Online analytical processing: large scans and aggregations across historical data, usually on columnar storage. (ch01)
- **Write-ahead log** — A sequential log of changes made durable before a database confirms a transaction; used for crash recovery, replication and CDC. (ch01)
- **Change data capture** — Reading a database's transaction log to emit each committed change as an event for downstream systems. (ch01)
- **Event streaming** — Moving events continuously between systems through a durable, partitioned, append-only log such as Apache Kafka. (ch01)
- **ELT** — Extract, load, transform: landing raw data first and transforming it inside the warehouse or lakehouse. (ch01)
- **Semantic layer** — A shared set of business definitions of metrics and entities used consistently by BI tools and AI agents. (ch01)
- **Vector index** — A data structure for fast approximate nearest-neighbor search over embeddings. (ch01)
- **Retrieval-augmented generation** — Fetching relevant content at query time and adding it to a language model's prompt (RAG). (ch01)
- **AI agent** — A model-driven program that plans and calls tools, including data queries, to complete a task. (ch01)
- **Model Context Protocol** — An open standard (MCP), introduced by Anthropic in 2024, for exposing tools and data sources to AI agents. (ch01)
- **HTAP** — Hybrid transactional/analytical processing: one system serving OLTP and OLAP workloads on fresh data (term coined by Gartner, 2014). (ch01)
- **Data catalog** — The registry of data assets, owners, lineage and access policies that spans every layer of the stack. (ch01)
- **Data gravity** — The tendency of large datasets to attract applications, compute and further data toward where they live. (ch01)
- **Workload** — The pattern in which software reads and writes data (size, frequency, latency and concurrency of operations). (ch01)
- **Zero-ETL** — Vendor-managed replication from an operational database into an analytical system that hides the pipeline from the user. (ch01)
- **Columnar storage** — storing each column's values contiguously so analytical queries read only the columns they need. (ch05)
- **Row store** — a layout that keeps all of a row's columns together on a page, suited to transactional reads and writes. (ch05)
- **Dictionary encoding** — compression that replaces repeated values with small integer codes plus a lookup table. (ch05)
- **Run-length encoding** — compression that stores a value once with a count of how many times it repeats consecutively. (ch05)
- **Delta encoding** — compression that stores differences between consecutive values instead of the values themselves. (ch05)
- **Bit-packing** — storing integers using only the minimum number of bits their range requires. (ch05)
- **Zone map** — per-chunk min/max statistics an engine checks to skip data that cannot match a filter. (ch05)
- **Late materialization** — deferring assembly of full rows until filters have reduced the data to the matching positions. (ch05)
- **Vectorized execution** — query processing that passes cache-sized batches of values between operators instead of one row at a time. (ch05)
- **Query compilation** — generating machine code for each query so operators fuse into tight loops (e.g., HyPer, Spark whole-stage codegen). (ch05)
- **Volcano iterator model** — the classic tuple-at-a-time execution design in which each operator pulls one row from its child via next(). (ch05)
- **SIMD** — single instruction, multiple data: one CPU instruction applied to many values held in a wide register. (ch05)
- **Massively parallel processing** — spreading a query across many nodes that each process a slice of the data in parallel (MPP). (ch05)
- **Shared-nothing** — an architecture in which each node owns its own CPU, memory and disk and holds a partition of the data. (ch05)
- **Shuffle** — redistributing rows across nodes by key so that related rows meet for a join or aggregation. (ch05)
- **Separation of storage and compute** — keeping durable data in shared (usually object) storage while stateless compute clusters scale independently. (ch05)
- **Virtual warehouse** — Snowflake's independently sized, stateless compute cluster that reads shared table data. (ch05)
- **Micro-partition** — Snowflake's immutable columnar storage unit (50–500 MB uncompressed) carrying per-column metadata for pruning. (ch05)
- **Managed storage** — vendor-operated tiered storage (local SSD cache plus object storage) behind a warehouse, as in Redshift RA3. (ch05)
- **Composable data stack** — building data systems from shared, interchangeable components such as Arrow, Velox and DataFusion. (ch05)
- **NDJSON** — Newline-delimited JSON: a text file with one self-contained JSON record per line, easy to stream but costly to parse. (ch06)
- **Apache Avro** — A row-oriented binary file and serialization format that embeds its schema and defines rules for reading data written under older schemas. (ch06)
- **Schema Registry** — A service (e.g., Confluent's) that stores versioned schemas for streaming topics and rejects changes that would break consumers. (ch06)
- **Apache ORC** — Optimized Row Columnar, a columnar file format created in 2013 by Hortonworks with Facebook to speed up Hive. (ch06)
- **Apache Parquet** — The default open columnar file format for analytics, created by Twitter and Cloudera in 2013 using Dremel's nested-data encoding. (ch06)
- **Row group** — A horizontal slice of rows in a Parquet file; the unit that predicate pushdown can skip as a whole. (ch06)
- **Column chunk** — The contiguous bytes of one column inside one Parquet row group, split into pages. (ch06)
- **Zstandard** — A general-purpose compression codec (zstd) that gives higher ratios than Snappy at similar decompression speed. (ch06)
- **Predicate pushdown** — Using file or row-group statistics (min/max, null counts) to skip data that a query's filter cannot match. (ch06)
- **Apache Arrow** — A language-neutral, in-memory columnar data layout that lets tools share data without converting it. (ch06)
- **Arrow Flight** — A gRPC-based protocol for streaming Arrow record batches between services without row-by-row serialization. (ch06)
- **ADBC** — Arrow Database Connectivity, a database client API that returns results as Arrow batches, a columnar counterpart to JDBC/ODBC. (ch06)
- **Zero-copy** — Handing data between components by sharing the same memory buffers instead of copying or converting them. (ch06)
- **Lance** — LanceDB's open columnar file format and table layer, designed for fast random access, versioning and multimodal/vector AI data. (ch06)
- **Vortex** — A compressed columnar file, memory and IPC format created by SpiralDB and hosted since 2025 by the LF AI & Data Foundation. (ch06)
- **Nimble** — Meta's open-source columnar file format aimed at very wide machine-learning feature tables. (ch06)
- **Safetensors** — A tensor file format (JSON header plus raw buffers) that can be memory-mapped and cannot execute code on load, unlike pickle checkpoints. (ch06)
- **WebDataset** — A training-data format that packs samples into tar shards so reads stay sequential while shards are shuffled. (ch06)
- **TFRecord** — TensorFlow's sequential record-stream file format for training examples. (ch06)
- **B-tree** — a shallow, wide, sorted tree of fixed-size pages used for indexes and tables; the common B+tree variant keeps all data in leaf pages linked left to right. (ch03)
- **Memtable** — the in-memory, sorted write buffer of an LSM-tree that is flushed to disk when full. (ch03)
- **SSTable** — a sorted string table: an immutable, sorted on-disk file produced by an LSM-tree flush or compaction. (ch03)
- **Bloom filter** — a compact probabilistic data structure that answers "definitely not present" or "maybe present" for a key. (ch03)
- **Write amplification** — the ratio of bytes physically written to storage to bytes the application logically wrote. (ch03)
- **Read amplification** — the number of storage reads a database performs per logical lookup. (ch03)
- **Space amplification** — the ratio of bytes stored on disk to bytes of live data. (ch03)
- **RUM conjecture** — the 2016 claim that an access method cannot minimize read, update and memory overhead all at once. (ch03)
- **Page split** — dividing a full B-tree page into two pages and inserting a new separator key into the parent. (ch03)
- **Fan-out** — the number of child pointers held by each internal page of a tree index, which sets the tree's height. (ch03)
- **Buffer pool** — the database's own in-memory cache of data and index pages. (ch03)
- **Group commit** — making several concurrently committing transactions durable with a single log flush. (ch03)
- **Fsync** — the operating-system call that forces buffered writes for a file onto stable storage. (ch03)
- **Checkpoint** — a point at which a database flushes dirty pages so crash recovery can start from there instead of the log's beginning. (ch03)
- **ARIES** — IBM's 1992 write-ahead-logging recovery algorithm with analysis, redo and undo passes. (ch03)
- **Isolation level** — a setting that defines which concurrency anomalies a database allows transactions to observe. (ch03)
- **Write skew** — an anomaly where two transactions read overlapping data, write different rows and together violate a rule neither violates alone. (ch03)
- **MVCC** — multi-version concurrency control: keeping several versions of a row so readers and writers do not block each other. (ch03)
- **Vacuum** — PostgreSQL's background process that reclaims space from dead row versions. (ch03)
- **Undo log** — storage holding prior images of changed rows, used for rollback and for reading older snapshots (Oracle, InnoDB). (ch03)
- **Two-phase locking** — a pessimistic concurrency protocol that acquires locks as needed and releases them only after commit. (ch03)
- **Secondary index** — an index on a column other than the primary key that points back to the table's rows. (ch03)
- **Covering index** — an index that contains every column a query needs, so the table itself need not be read. (ch03)
- **Bitmap index** — an index storing one bit-vector per distinct column value, suited to low-cardinality analytic filters. (ch03)
- **Query optimizer** — the database component that chooses an execution plan for a query, usually by estimating costs. (ch03)
- **Cardinality estimation** — predicting how many rows each step of a query plan will produce. (ch03)
- **Volcano model** — row-at-a-time query execution in which each operator pulls rows from its child through a next() call. (ch03)
- **EXPLAIN** — the SQL command that shows the execution plan the optimizer chose, optionally with actual run-time statistics. (ch03)
- **Page** — the fixed-size block (for example 8 kB in PostgreSQL, 16 KB in InnoDB) that is a database's unit of I/O and caching. (ch03)
- **Clustered index** — a table stored as a B-tree ordered by its primary key, with full rows in the leaves (as in InnoDB). (ch03)
- **Tombstone** — a marker written in an LSM-tree to record a deletion until compaction removes the key. (ch03)
- **Sharding** — splitting a dataset into partitions stored on different nodes so capacity scales out. (ch04)
- **Consistent hashing** — placing nodes and keys on a hash ring so adding or removing a node moves only a small share of keys. (ch04)
- **Hot spot** — a shard or key that receives disproportionate traffic and limits the throughput of the whole cluster. (ch04)
- **Replication** — keeping copies of the same data on several nodes for durability and availability. (ch04)
- **Replication lag** — the delay between a write committing on the leader and becoming visible on a replica. (ch04)
- **Multi-leader replication** — a topology in which several replicas accept writes and exchange them, so conflicting writes must be resolved. (ch04)
- **Leaderless replication** — a Dynamo-style topology in which clients write to and read from quorums of replicas directly, with no single leader. (ch04)
- **Quorum** — the minimum number of replicas, usually a majority, that must acknowledge an operation for it to count. (ch04)
- **Consensus** — a protocol by which a group of replicas agrees on a single ordered log of operations despite crashes and message delays. (ch04)
- **Paxos** — Leslie Lamport's consensus protocol, used in production as Multi-Paxos by Spanner and many Google systems. (ch04)
- **Raft** — a consensus protocol designed for understandability, built from leader election, log replication and majority commit. (ch04)
- **Two-phase commit** — an atomic-commit protocol in which a coordinator collects prepare votes and then issues commit, blocking if it fails mid-protocol. (ch04)
- **TrueTime** — Google's clock API, backed by GPS and atomic clocks, that returns a bounded interval of possible current times. (ch04)
- **External consistency** — the guarantee that transaction commit order matches real-time order across the whole system, as in Spanner. (ch04)
- **Hybrid logical clock** — a timestamp combining physical clock time with a logical counter, used by CockroachDB and YugabyteDB to order events without special hardware. (ch04)
- **Timestamp oracle** — a central service that issues strictly increasing transaction timestamps, as in Percolator and TiDB's Placement Driver. (ch04)
- **CAP theorem** — the result that a replicated system facing a network partition must choose between consistency and availability. (ch04)
- **PACELC** — Abadi's extension of CAP: under a partition choose availability or consistency, else choose latency or consistency. (ch04)
- **Linearizability** — a consistency model in which every operation appears to take effect at one instant consistent with real time. (ch04)
- **Eventual consistency** — a consistency model promising only that replicas converge once writes stop. (ch04)
- **NewSQL** — distributed databases that offer SQL and ACID transactions at horizontal scale, also called distributed SQL. (ch04)
- **Disaggregated storage** — an architecture separating stateless compute from a shared storage service; in Aurora and Neon the storage consumes the database log. (ch04)
- **Data sovereignty** — legal requirements that certain data be stored and processed within a particular jurisdiction. (ch04)
- **ETL** — Extract, transform, load: data is cleaned and reshaped on a separate system before it is loaded into the warehouse. (ch09)
- **Log-based CDC** — Change data capture that reads the database's recovery log (Postgres WAL, MySQL binlog, Oracle redo) instead of querying tables. (ch09)
- **Query-based CDC** — Change data capture that polls tables for rows with a newer timestamp or ID; simple but misses hard deletes. (ch09)
- **Trigger-based CDC** — Change data capture that uses database triggers to copy each change into a shadow table, at a cost to every write. (ch09)
- **Replication slot** — A Postgres object that makes the primary retain write-ahead log until a consumer confirms it has read it. (ch09)
- **Binlog** — MySQL's binary log of committed changes, used for replication and change data capture. (ch09)
- **Micro-batch** — Processing a stream as a rapid series of small batch jobs, typically every few seconds to minutes. (ch09)
- **Event time** — The time an event actually occurred, as opposed to the processing time at which the system observed it. (ch09)
- **Watermark** — A stream processor's running estimate that all events up to a given event time have arrived, used to decide when to emit window results. (ch09)
- **Late data** — Events that arrive after the watermark has passed the end of their window, and are either dropped or used to correct results. (ch09)
- **Exactly-once semantics** — A pipeline guarantee that each event affects the final result exactly once despite retries, achieved via deduplication or transactions. (ch09)
- **Idempotency** — The property that running an operation more than once produces the same result as running it once. (ch09)
- **Backfill** — Reprocessing historical data to fill gaps or apply corrected logic to past periods. (ch09)
- **Incremental snapshot** — A chunked, lock-free copy of a table that is interleaved with a live CDC stream using watermark markers (DBLog/Debezium). (ch09)
- **Reverse ETL** — Syncing modeled data from the warehouse back into operational SaaS tools such as CRM and ad platforms. (ch09)
- **Data mirroring** — Continuous, vendor-managed replication of an operational database into an analytics platform (e.g., Fabric mirroring, Snowflake Postgres mirroring). (ch09)
- **Zero-copy data sharing** — Granting another account or organization query access to data in place, without duplicating it. (ch09)
- **Query federation** — Querying external databases in place by pushing queries down to them rather than copying their data. (ch09)
- **OpenSharing** — Linux Foundation open protocol for sharing data and AI assets across platforms, the successor to Delta Sharing (2026). (ch09)
- **Delta Sharing** — Open REST protocol (2021) that shares tables by handing recipients short-lived signed URLs to the underlying files; now OpenSharing. (ch09)
- **Medallion architecture** — Layering data into bronze (raw), silver (cleaned and conformed) and gold (business-ready) tables. (ch09)
- **Monthly active rows** — Fivetran's billing unit: distinct rows inserted, updated or deleted in a month, tiered per connection since March 2025. (ch09)
- **Connector** — code that extracts data from one source type (SaaS API, database, file) and emits standardized records to a destination. (ch10)
- **Incremental sync** — fetching only the records that changed since the last successful sync. (ch10)
- **Cursor field** — a column such as updated_at that a connector uses to find changed records. (ch10)
- **State store** — where a pipeline records its progress (cursor values, log offsets) so it can resume without gaps or duplicates. (ch10)
- **Schema drift** — unplanned changes in a source's columns or data types that a pipeline must detect and handle. (ch10)
- **Rate limit** — a cap on API calls per time window imposed by a source system. (ch10)
- **Informatica Processing Unit** — Informatica's pre-paid, pooled consumption unit that can be spent across IDMC services. (ch10)
- **DPU-hour** — AWS Glue's billing unit: one data processing unit of compute running for one hour. (ch10)
- **Capacity-based pricing** — billing for reserved processing capacity rather than for data volume moved. (ch10)
- **Connector SDK** — a development kit for writing custom connectors that a vendor's managed runtime hosts and meters. (ch10)
- **Singer** — an open specification for "taps" (sources) and "targets" (destinations) that exchange JSON records; the basis of Meltano. (ch10)
- **iPaaS** — integration platform as a service, used mainly to connect operational applications through APIs and events. (ch10)
- **Append-only log** — An ordered sequence of records that is only ever appended to, with readers tracking their position by offset. (ch11)
- **Topic** — A named stream in Kafka, made up of one or more partitions. (ch11)
- **Partition** — An independently ordered shard of a Kafka topic and the unit of parallelism and ordering. (ch11)
- **Offset** — The sequential position number of a record within a partition. (ch11)
- **Broker** — A Kafka server that stores partitions and serves producer writes and consumer reads. (ch11)
- **In-sync replicas** — The replicas fully caught up with a partition's leader (ISR); all must hold a write before an acks=all acknowledgment. (ch11)
- **Consumer group** — A set of consumers that divide a topic's partitions among themselves, with the group tracking its own committed offsets. (ch11)
- **Share group** — Kafka 4.x queue-style consumption (KIP-932) in which several consumers process records from the same partition with per-record acknowledgment. (ch11)
- **Log compaction** — A Kafka retention mode that keeps only the latest record for each key, turning a topic into a changelog of current state. (ch11)
- **KRaft** — Kafka's built-in Raft-based metadata quorum, which replaced ZooKeeper and became mandatory in Kafka 4.0. (ch11)
- **Idempotent producer** — A Kafka producer that stamps batches with sequence numbers so broker-side deduplication makes retries harmless. (ch11)
- **Tiered storage** — Offloading older log segments from broker disks to object storage while keeping recent data local (Kafka KIP-405). (ch11)
- **Diskless Kafka** — Kafka-compatible designs whose primary store is object storage and whose brokers are stateless (e.g., WarpStream, KIP-1150). (ch11)
- **Bring your own cloud** — A deployment model (BYOC) in which a vendor's data plane runs inside the customer's own cloud account. (ch11)
- **Inter-AZ data transfer** — The per-GB cloud charge for network traffic between availability zones in the same region. (ch11)
- **Stream processing** — Continuous computation such as filters, joins and aggregations over unbounded event streams. (ch11)
- **Streaming database** — A database that keeps SQL materialized views continuously up to date from incoming streams (e.g., RisingWave, Materialize). (ch11)
- **dbt** — Open-source framework that compiles SQL-plus-Jinja "models" into a dependency graph and runs them inside a warehouse or lakehouse. (ch12)
- **Analytics engineering** — The discipline of applying software practices (version control, code review, CI, tests) to SQL data transformation. (ch12)
- **Directed acyclic graph** — A graph of tasks or models connected by one-way dependency edges with no cycles, used to determine run order. (ch12)
- **Materialization** — How a dbt model's result is persisted: as a view, table, incremental table or ephemeral CTE. (ch12)
- **Incremental model** — A transformation that processes only new or changed rows and merges them into an existing table instead of rebuilding it. (ch12)

- **Customer concentration** — the share of a company's revenue that comes from its largest customers, a measure of how much one renewal can move the business. (ch47)
- **Logo churn** — the share of customers lost in a period, counted by account rather than by dollars. (ch47)
- **Key-person risk** — the value a company loses if a few individuals, such as founders or core engineers, leave. (ch47)
- **Multi-tenancy** — serving many customers from shared infrastructure while keeping their data and workloads isolated from one another. (ch47)
- **Vendor lock-in** — the cost and difficulty a customer faces in leaving a vendor's data format, catalog or contract. (ch47)
- **Listen-for note** — in the Ch 48 question bank, a short description of what a strong answer to a question contains, used as a scoring key after the meeting. (ch48)
- **Apache Hudi** — an open table format created at Uber, built around a timeline of table actions and tuned for upserts and streaming ingestion. (ch49)
- **Apache Kafka** — an open-source distributed, partitioned log in which producers append events to topics and many consumers read them independently; the default event-streaming backbone. (ch49)
- **Apache Flink** — an open-source stream-processing engine that runs continuous joins, aggregations and windows over events with managed state and exactly-once guarantees. (ch49)
- **EU AI Act** — Regulation (EU) 2024/1689, the EU's risk-tiered AI law, whose high-risk duties include training-data governance (Article 10), now applying from December 2027 and August 2028 after the 2026 AI Omnibus. (ch49)
